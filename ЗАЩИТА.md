# Защита базы и сервера (живой чек-лист)

Отмечаю выполненное по мере работы. Всё делается так, чтобы переезд на другой VPS
занимал минимум времени: настройки сервера собраны в скрипты в папке `selfhost/`,
их достаточно запустить один раз на новом сервере.

## Уже в порядке (проверено на сервере)

- [x] Пароли в базе шифруются современным способом (scram-sha-256).
- [x] Соединение с базой шифруется (SSL включён).
- [x] Приложение подключается не под главным пользователем базы, а под отдельным `crm` без прав администратора.
- [x] Fail2ban на сервере запущен.
- [x] Ночные копии базы делаются каждый день в 03:30, хранятся 14 дней.

## Этап 1. Закрыть базу от интернета

- [x] Подготовлен скрипт `selfhost/server-hardening.sh`: закрывает порт базы файрволом,
      переводит базу на локальный адрес, чистит внешние разрешения, настраивает fail2ban
      на подбор пароля к серверу и к базе, ужесточает права на копии.
- [ ] Скрипт запущен на сервере под root (у моего доступа нет прав администратора — нужен ваш запуск или доступ).
- [ ] Проверено, что сайт и приложение работают, а снаружи база недоступна.

## Этап 2. Копии вне сервера

- [x] Подготовлен скрипт `selfhost/backup-offsite.sh`: копия базы шифруется паролем
      и выгружается во внешнее хранилище (S3), хранение 14 дневных + недельные + месячные,
      проверка размера копии, письмо-отчёт на почту.
- [x] Подготовлен файл настроек `selfhost/backup.env.example` (переносится на любой VPS).
- [x] Подготовлен скрипт восстановления `selfhost/restore.sh` с проверкой количества строк.
- [ ] Подключено внешнее хранилище S3 (нужно ваше решение: подключить хранилище через Lovable или дать ключи).
- [ ] Скрипт установлен на сервер и поставлен в ночное расписание.
- [ ] Выполнен тест восстановления из копии.

## Этап 3. Вход на сервер

- [x] Ужесточение входа включено в `selfhost/server-hardening.sh`: только по ключу,
      вход под root по сети запрещён, ограничение попыток.
- [ ] Применено на сервере (требуются права администратора).

## Этап 4. Разделение данных клиентов (для продажи доступа)

- [x] Ограничение попыток входа в приложение: 8 неудачных попыток за 15 минут по почте
      или по адресу — вход временно блокируется; попытки пишутся в базу.
- [ ] Проверка принадлежности данных на уровне самой базы (политики по «базе» клиента),
      чтобы чужие данные были недоступны даже при ошибке в программе.
- [ ] Расширить журнал: кто и когда открывал важные разделы.

## Этап 5. Перед продажей

- [x] Ежедневное письмо-отчёт о копии базы: `selfhost/monitor.sh`, запуск каждый день в 08:00,
      письмо приходит на dir@doormail.ru; проверено вручную 19.09.
- [x] Контроль свободного места и доступности сайта — в том же `monitor.sh` (диск, HTTP 200, процесс crm).
- [x] Инструкция по восстановлению и переезду на другой VPS: `selfhost/restore.sh` + `selfhost/ПЕРЕЕЗД.md`.
- [x] В админке исправлена пустая «Состояние базы» (запросы падали на типах полей);
      «Активные сессии» заменены на «Неудачных входов за сутки».

## Что нужно от вас

1. Запустить один раз на сервере под администратором: `sudo bash selfhost/server-hardening.sh`
   (или дать мне доступ с правами администратора — тогда сделаю сам).
2. Решить, куда складывать копии вне сервера: подключить S3-хранилище через Lovable
   или передать ключи доступа к вашему хранилищу.
3. Придумать и сохранить отдельно (не на сервере) пароль шифрования копий.

## Переезд на другой VPS

Порядок: установить PostgreSQL и Node, скопировать папку приложения и `.env`,
восстановить базу через `selfhost/restore.sh`, запустить `selfhost/server-hardening.sh`,
положить `/etc/crm-backup.env` и поставить `selfhost/backup-offsite.sh` в расписание.
