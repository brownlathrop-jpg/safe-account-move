# База данных на своём сервере вместо Firebase

## Что показал ваш сервер (178.212.13.144)

| Что | Сейчас | Оценка |
| --- | --- | --- |
| Процессор | 2 ядра Xeon 3.1 ГГц | хватает с запасом (загрузка почти нулевая) |
| Память | 4 ГБ, свободно ~2,6 ГБ, но уже используется 1,1 ГБ подкачки | узкое место, лучше добавить до 8 ГБ |
| Диск | 30 ГБ, свободно 10 ГБ | на базу хватит, на бэкапы — впритык |
| Нагрузка | 0,02 из 2 — сервер почти простаивает | места для базы достаточно |

Вывод: **мощности хватит.** Ваши данные — около 15 тысяч записей, это меньше 100 МБ; даже с ростом в 20 раз это единицы гигабайт. Единственное, что стоит подтянуть, — память: сейчас сервер уже частично уходит в подкачку, а база любит свободную память. Добавить 4 ГБ у хостинга — обычно 300–500 ₽/мес. Это всё равно в 15–20 раз дешевле облака Яндекса.

## Плюсы и минусы

**Плюсы**
- Стоимость: 0 ₽ дополнительно (сервер у вас уже оплачен), против ~30 000 ₽/мес в Яндексе.
- Никаких лимитов на чтение и запись — сегодняшняя проблема «Quota exceeded» исчезает навсегда.
- База и приложение на одной машине — запросы отвечают за доли миллисекунды.
- Оплата в рублях, данные в России.
- Полный контроль: любые отчёты, выгрузки, прямой доступ к данным.

**Минусы**
- Нет автоматической отказоустойчивости: если сервер упадёт, CRM недоступна, пока он не поднимется.
- Бэкапы и обновления — наша ответственность (решается расписанием и копией на внешнее хранилище).
- Один сервер тянет и сайт, и базу — при сильном росте придётся расширять или разделять.
- Переезд с Firebase — заметный объём работы (см. ниже).

Компромисс, который снимает главный минус: ежедневный бэкап в объектное хранилище (Яндекс Object Storage ~2 ₽/ГБ в месяц, то есть рубли в месяц), чтобы при аварии восстановиться на любом новом сервере за час.

## План переезда

1. **Подготовка сервера** — установить PostgreSQL 16, настроить под 4–8 ГБ памяти, закрыть доступ извне (база слушает только localhost), включить ежедневный бэкап + отправку копии во внешнее хранилище.
2. **Схема данных** — перенести все справочники и документы в таблицы: товары, папки, накладные, позиции, контрагенты, склады, движения склада, касса, статусы, рабочие пространства. Разделение по пользователям — через `workspace_id` в одной базе (не отдельные базы на каждого сотрудника).
3. **Вход в систему** — свой вход по email и паролю с восстановлением по письму, вместо Firebase Auth. Ваш текущий логин переносим, пароль задаётся заново по письму.
4. **Слой доступа к данным** — переписать внутренний слой так, чтобы вся CRM работала с PostgreSQL. Экраны и логика остаются те же, меняется «под капотом».
5. **Перенос данных** — выгрузить всё из Firebase и залить в PostgreSQL, сверить количество записей по каждому разделу (как делали при переезде из Supabase).
6. **Проверка и переключение** — прогнать основные сценарии: товары, папки, накладные, проведение склада, касса, печать. Затем деплой и отключение Firebase.
7. **После переезда** — включить бэкапы по расписанию, проверить восстановление из копии.

## Технические детали

- PostgreSQL 16 из apt, `shared_buffers` 1 ГБ, `work_mem` 16 МБ, `max_connections` 50; только `listen_addresses = localhost`.
- Приложение подключается через переменную `DATABASE_URL`, запросы — через серверные функции TanStack Start (`createServerFn`), без прямого доступа из браузера.
- Авторизация: сессия в httpOnly-cookie, пароли — bcrypt/argon2, письма восстановления через существующий почтовый канал.
- Изоляция данных: `workspace_id` в каждой таблице + проверка на сервере в каждом запросе (аналог текущих правил).
- Бэкап: `pg_dump` по cron ежедневно, хранение 14 дней локально + выгрузка в S3-совместимое хранилище.
- Миграция: скрипт-выгрузка из Firestore REST в JSON, затем пакетная вставка в PostgreSQL с сверкой количества.

## Что нужно от вас

- Решение: расширять память сервера до 8 ГБ или пока оставить 4 ГБ.
- Пароль root/sudo для установки PostgreSQL (сейчас у `crmdeploy` есть права только на панель).
